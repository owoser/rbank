# rbank 跨服经济插件 — 架构设计

MCBE / LeviLamina / 基于 LegacyMoney 二开 / MySQL 8

---

## 1. 不变量（一切设计从这里推导）

| # | 不变量 | 推导出的约束 |
|---|---|---|
| I1 | 玩家唯一身份 = **xuid** | 所有表以 xuid 为资金主键；不复用名称、UUID |
| I2 | 原版余额（LegacyMoney）**分服独立**，银行是唯一跨服钱包 | 原版写入只能在「玩家当前所在服的进程内」发生 |
| I3 | 原版接口无事务、无跨进程锁，且为同步阻塞 | DB 事务无法包裹原版调用 → 资金搬运只能是 **Saga**，不能是 2PC |
| I4 | 多给（凭空造币）比少给（挂账）危害高一个量级 | 任何方向都 **先扣减来源，后增加目标**，失败再补偿 |
| I5 | 卡余额以**基准单位整数**记账，汇率为正整数 | 全流程整数运算，无浮点；舍入靠「整倍校验」消除 |
| I6 | 同一 xuid 的资金操作必须全局串行 | 跨进程互斥依赖 DB（行锁 / `GET_LOCK`），不依赖内存锁 |
| I7 | 指令、Form、HTTP 行为必须一致 | 三条通道只做参数解析与呈现，业务规则全在 Core |
| I8 | 银行**不介入**游戏内经济 | 原版写入只出现在 `deposit` / `withdraw` 两条路径；审计为只读旁路 |
| I9 | 规模 ≤5 服 / ≤200 人峰值 | 不做缓存层、分库分表、读写分离；单库 + 连接池足够 |

## 2. 已定决策

| 项 | 结论 |
|---|---|
| 身份 | xuid（Xbox UID） |
| 资金边界 | 各服 LegacyMoney 独立；银行是跨服唯一钱包；游戏内消费、掉落、商店全部走原版 |
| 卡余额模型 | **单一余额**，基准单位整数记账；存入按汇率折算，取出按汇率还原 |
| 汇率语义 | `rate = 本服货币 / 基准单位`（正整数）。A 服 100、B 服 1000：A 存 100 → 余额 +1；B 取 1 → 到账 1000 |
| 基准单位 | 整数计数，精度固定；**显示名是可热更配置**（`base_unit`，默认 `Base`），只影响界面与文案，不改换算比例 |
| 整倍约束 | 存入/取出金额必须是 `rate` 的整数倍，否则**拒绝并要求重输** |
| 手续费 | 一律在基准单位层计收并**直接销毁**（不进入任何账户） |
| 计费口径 | **同服免费、跨服收费**；判定依据为卡内 base 的**来源服批次（lot）** |
| 卡槽 | 全局卡槽池，上限由 DB 配置热更，默认 1 张 |
| 删卡 | 余额必须为 0，否则拒绝 |
| 转账 | 银行内两账户划转，不触碰原版；收款方**必须已有卡**，否则拒绝并提示 |
| 节点身份 | 插件配置固定 `server_id / server_name / currency`；启动自动入库，存在则校验一致性 + 心跳 |
| DB 访问 | 插件直连 MySQL（连接池 + 专用线程池 + 事务） |
| HTTP | 每服内嵌，**默认关闭**；运维在指定一服开启即可 |
| 审计 | 银行域流水 + 订阅 LegacyMoney after 事件采集原版全量变动（只读旁路，失败丢弃） |
| 汇率调整 | 仅公告，不冻结存取；变更记入 `rate` 表并全服广播 |
| 玩家交互 | `/rbank` 指令树 + Form 表单；入服自动展示卡信息与最近 3 条流水 |

## 3. 分层

```
┌───────────────────────── adapter 接入适配 ─────────────────────────┐
│ command(/rbank) │ form(Form UI) │ event(join/LLMoney) │ http(可选) │
└───────────────────────────────┬───────────────────────────────────┘
                                │ 统一 Result{code,message,data}
┌───────────────────────────────▼───────────────────────────────────┐
│ core 领域与用例（纯逻辑，不依赖 MC / MySQL）                        │
│  model: Card Lot LedgerEntry TransferIntent Node Rate AuditRecord  │
│  port : CardRepo LotRepo LedgerRepo NodeRepo RateRepo AuditRepo    │
│         UnitOfWork MoneyGateway Clock IdGen ConfigStore            │
│  service: CardService CashierService TransferService               │
│           FeePolicy SlotService AuditService                       │
└───────┬───────────────────────────────────────▲───────────────────┘
        │ 实现端口                              │ 调用用例
┌───────▼───────────── infra 基础设施 ──────────┴───────────────────┐
│ mysql(连接池/事务/仓储/迁移) │ legacymoney(LLMoney C API + 事件桥)  │
│ cardgen(卡号规则 DSL)        │ runtime(线程池/调度/RecoveryWorker)  │
└──────────────────────────────────────────────────────────────────┘
┌────────────────────── proto 跨服协议 ─────────────────────────────┐
│ 节点注册/心跳 │ 汇率统一管理 │ 审计上报 │ 幂等键与搬运单约定        │
└──────────────────────────────────────────────────────────────────┘
```

依赖方向单向：`adapter → core ← infra`。`core` 不 include 任何 `ll/` 或 `mysql` 头文件。

**I8 的执行点**：`MoneyGateway` 只暴露 `Get / Add / Reduce`，不暴露 `Set`，不注册任何 before 事件拦截。原版经济行为对插件不可见、不可改。

## 4. 数据模型（MySQL 8，库名 `rbank`）

| 表 | 关键列 | 说明 |
|---|---|---|
| `node` | `server_id` PK, `server_name`, `currency`, `plugin_ver`, `last_heartbeat`, `status` | 启动自动注册；同名不一致则告警并降级只读 |
| `rate` | `id` PK, `server_id`, `rate_bigint`, `effective_at`, `set_by` | 追加式历史表；当前汇率 = `effective_at <= now()` 的最新一条 |
| `config` | `k` PK, `v` JSON, `version`, `updated_by`, `updated_at` | 热更配置：卡槽上限、费率、限额、功能开关 |
| `card` | `card_no` PK, `xuid`, `slot_index`, `balance_base` BIGINT, `version`, `status` | `UNIQUE(xuid, slot_index)`；`balance_base` 为 `lot` 的冗余汇总 |
| `card_lot` | `id` PK, `card_no`, `base_amount`, `remain_base`, `origin_server_id`, `created_at` | 资金批次，来源服判定依据；余额 = `SUM(remain_base)` |
| `intent` | `intent_id` PK, `xuid`, `dir`, `card_no`, `base_amount`, `fee_base`, `local_amount`, `rate`, `server_id`, `state`, `attempts`, `error`, `request_key` UNIQUE | 资金搬运单（Saga 日志）；`request_key` 承担幂等，`state` 承担恢复 |
| `ledger` | `id` PK, `xuid`, `card_no`, `kind`, `delta_base`, `fee_base`, `balance_after`, `rate`, `local_amount`, `server_id`, `peer_xuid`, `intent_id`, `created_at` | 银行域流水；与资金动作同事务写入 |
| `audit_legacy` | `id` PK, `xuid`, `evt`, `delta`, `balance_after`, `server_id`, `created_at` | 原版资金变动镜像（异步批量落库） |
| `card_gen_seq` | `k`, `v` | 卡号规则用到序列字段时使用 |

金额一律 `BIGINT`；不用 `FLOAT/DOUBLE`。

`card_lot` 是「同服免费」的唯一裁决依据：余额是单一数字，但每笔 base 携带来源服标签，取款时据此分档计费。

## 5. 资金协议（核心）

### 5.1 两个方向，顺序相反且不可互换

**存款（原版 → 银行）**
```
1 校验：卡归属 / 状态 / local % rate == 0 / 单笔与日限额 / 手续费后 base > 0
2 原版 Reduce(xuid, local)            ← 先扣来源；失败即终止，无副作用
3 intent(PENDING_DB) + DB 事务：
    lot 新增(base_amount = local/rate, origin_server_id = 本服)
    card.balance_base += 入账额, 写 ledger, intent = SETTLED
4 步骤 3 失败 → 重试；超阈值 → 原版 Add 全额回滚, intent = ROLLED_BACK
```

**取款（银行 → 原版）**
```
1 校验：卡归属 / local % rate == 0 / 可用余额 / 手续费
2 DB 事务（持卡行锁）：
    按「同服 lot 优先，其余 FIFO」消耗 lot
    card.balance_base -= 扣除额, 写 ledger, intent = PENDING_LEGACY
3 原版 Add(xuid, local)               ← 后加目标；失败 → DB 补偿加回, intent = ROLLED_BACK
4 成功 → intent = SETTLED
```

为什么方向不能反：存款若先加 DB，玩家可断线/关服逃逸扣款 → 造币；取款若先加原版，玩家可并发多服重复取 → 造币。**先扣来源是唯一安全序。**

### 5.2 整倍约束与手续费

基准单位精度固定为整数，任何非整倍折算都会产生无法归属的余数，因此：

- 玩家输入的金额必须是 `rate` 的整数倍，否则**拒绝并提示「本服最小可操作金额为 rate」**，不做静默截断。
- 手续费一律在 base 层计收：`fee = ceil(base × rate_cfg) + fixed_cfg`，四舍五入方向向上，且 `fee < base` 否则拒绝（"手续费超过本金"）。
- **手续费直接销毁**：只减少 lot 与 `balance_base`，不产生任何入账方，不进 `ledger` 的对手方账户。

| 动作 | 计费基数 | 说明 |
|---|---|---|
| 存款 | `base` | 本金 full Reduce，入账 `base - fee` |
| 取款（同服 lot） | — | 免费，`local = base × rate` |
| 取款（异服 lot） | 该部分 `base` | 按跨服费率计收，到账金额由玩家指定，手续费额外从余额扣 |
| 转账 | 划转 `base` | 银行内划转，无 server 概念，按转账费率统一计收 |

### 5.3 转账

玩家 `pay` 是**纯银行内两账户划转**，单 DB 事务完成，不调用 `LLMoney_Trans`：

1. 解析收款标识（卡号，或玩家 ID → 其 slot 0 卡）
2. 收款方**无卡则拒绝**，提示「对方未开通银行卡」
3. 同事务：源卡扣 base + fee，目标卡入 base，lot 迁移（改 `card_no`，**保留 `origin_server_id`**）
4. 写双向 `ledger`，并登记一张 `dir = Transfer` 的单据（只用于幂等去重与留痕）

lot 保留来源服标签，意味着转账不会把异服资金"洗成"本服资金，免费额度不可通过转账套取。

### 5.4 幂等与恢复

**幂等键**：`intent.request_key`（唯一索引，`NULL` 不占用）。

- 键由「一次请求」产生，不由参数产生 —— 同一玩家连存两笔 100 是两笔合法操作，按内容去重会吞掉真实意图。
- 键的来源：**表单打开时生成一次**，该表单的所有回调复用同一键；指令每次敲击都是新请求，故传空、不参与去重。
- 判定交给数据库：`INSERT` 撞唯一索引即失败，发生在**任何扣款之前**，因此无需补偿，直接返回「该操作已处理」。
- 先查后做不可行：查与做之间仍有竞态。

**状态迁移**：唯一入口是 `compareAndSet(id, from, to)`，SQL 为
`UPDATE intent SET state=? WHERE intent_id=? AND state=?`，`ROW_COUNT() = 0` 即视为已被他人接管，调用方立即放弃。

- CAS 是入账/补偿事务的**第一条语句**，抢不到就整笔回滚，因此并发恢复与正常路径最多只有一方能改账。
- 转账复用同一张 intent 表（`dir = Transfer`），因此双击 `/rbank pay` 同样被挡住。

**恢复**：`RecoveryWorker`（每 30s）扫描超过宽限期仍未终结的单据：

- 存款 `PendingDb` → 原版已扣、银行未入账 → 前滚
- 存款 `PendingLegacy` → 原版未确认扣减 → 放弃（窗口极小，属「少给」方向）
- 取款 `PendingDb` → 银行已扣、原版未加 → 补偿回滚
- 归属节点长期离线 → 标记 `ORPHAN`，由 HTTP 管理接口人工处置

崩溃窗口只可能造成「挂账」，不可能造成「造币」。这是 I4 的兑现方式。

> 早期设计写的是「`intent_id` 由 xuid + 动作 + **客户端序列**派生」。MC 的指令与表单没有客户端序列，重发也不保证编号不变，该方案在本平台不可实现，已废弃。


### 5.5 并发

- xuid 维度互斥：`SELECT ... FOR UPDATE` 锁 `card` 行 + `GET_LOCK('rbank:xuid:<xuid>')`，避免同 xuid 多卡与多服竞争。
- 卡槽占用 = `COUNT(card WHERE xuid=? AND status='ACTIVE')`，在持锁事务内计算。
- lot 消耗与 `balance_base` 更新必须同事务，否则汇总值与批次不一致。

## 6. 卡号生成

配置驱动，编译期不写死规则：

```json
"card_no": {
  "length": 12,
  "fields": ["SERVER_CODE:2", "RANDOM_ALNUM:8", "SEQ:2"],
  "alphabet": "0123456789ABCDEFGHJKLMNPQRSTUVWXYZ",
  "server_code": "A1",
  "checksum": "LUHN10"
}
```

字段类型：`RANDOM_UPPER` / `RANDOM_LOWER` / `RANDOM_DIGIT` / `RANDOM_ALNUM` / `SERVER_CODE` / `XUID_HASH` / `SEQ`。
约束：`alphabet` 默认剔除 `I O 0 1`；`checksum` 用于卡号手输防错；唯一性靠 `card.card_no` 主键 + 生成重试（默认 5 次）。

## 7. 配置分域

| 域 | 载体 | 生效 | 内容 |
|---|---|---|---|
| 启动配置 | `config/config.json`（只读） | 需重启 | 数据库连接、`server_id/server_name/currency`、卡号规则、线程池、日志、HTTP 监听与开关 |
| 热更配置 | `config` 表 | 秒级（30s 缓存 + 版本号） | 卡槽上限、基准单位显示名、存款/取款/跨服/转账费率、固定手续费、单笔与日限额、功能开关 |
| 汇率 | `rate` 表 | 秒级 | 各服 `rate_bigint`；写入即广播公告 |

已完成动作永久快照当时 `rate` 到 `ledger`，调汇率不影响历史流水。

## 8. 接入适配层契约

三条通道统一转换为 Core 用例调用，返回 `Result{code, message, data}`：

| 通道 | 能力 |
|---|---|
| `/rbank` 指令 | `create/delete/list/info/deposit/withdraw/pay/hist/rate/slot/baseunit`；玩家子集 + OP 子集 + 控制台子集 |
| Form | 卡列表 → 选卡 → 存/取/转/流水/删卡；入服自动弹窗（可配关闭） |
| HTTP | 读：卡、流水、节点、汇率、配置。写：**仅管理域**（冻结卡、改配置、调汇率、处置 ORPHAN）。**不开放玩家存取转** |
| 事件 | 入服钩子、LegacyMoney `after` 事件 → 审计 |

所有原版调用经 `MoneyGateway` 端口，实现内调度到服务端主线程；DB 操作在独立线程池，完成后回主线程做原版写入。

HTTP 管理接口的端点、鉴权、错误码与排障流程见[接口文档](./接口文档.md)。

## 9. 故障矩阵

| 故障 | 结果 | 处置 |
|---|---|---|
| DB 不可用 | **银行域**操作快速失败（"银行维护中"）；**原版经济不受任何影响** | 熔断；审计旁路静默丢弃 |
| 审计写库异常 | 原版资金动作照常完成 | 丢弃 + 采样日志；**异常不得回传原版调用栈** |
| 存款第 3 步失败 | 玩家已扣原版、余额未加 | intent 保留 → RecoveryWorker 前滚/回滚 |
| 取款第 3 步失败 | 银行已扣、原版未加 | DB 补偿加回 |
| 服务器崩溃 | intent 停留中间态 | 重启后扫描本服 intent 恢复 |
| 汇率缺失/为 0 | 拒绝折算，提示"本服汇率未配置" | 校验期拦截 |
| 金额非 rate 整倍 | 拒绝，提示最小可操作金额 | 输入期校验 |
| 节点 `server_id` 冲突 | 拒绝启动（只读降级） | 运维改配置 |
| 卡号重试耗尽 | 创建失败并记录 | 提示改规则或扩容 alphabet |

## 11. 已知风险与后续

| 项 | 说明 |
|---|---|
| 汇率套利 | 余额以 base 计价，取款时才按当时 `rate` 折算。调汇率前玩家存入、调后取出即可套利。已决定仅公告不冻结，**属运营纪律问题**：调汇率前必须公告并预判存量。 |
| 同服免费额度 | lot 携带来源服标签，玩家无法通过「转入同服卡」洗白；但跨服取款后再存回本服会生成新的本服 lot，属于正常行为。 |
| 基准单位改名 | `base_unit` 只改显示名，换算比例不变。改名前后流水共用同一套数字，玩家旧截图里的单位名会与新界面不同。 |
| 待扩展 | 日终对账（原版余额 + 卡余额 vs 流水净额）、卡冻结风控、多基准币种 |
